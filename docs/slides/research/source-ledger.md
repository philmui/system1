## Layers: a teaching map, not a compatibility map

| Layer | Role | LangChain example | Salesforce framing |
| --- | --- | --- | --- |
| Decision or generation model | Computes a learned result | Jev or a generative model | `koa-action` or a generative model |
| Runtime | Executes steps and manages workflow state | LangGraph | Agent Graph |
| Framework / integrations | Offers abstractions and reusable connections | LangChain | No direct one-to-one equivalence asserted |
| Harness | Selects context, tools, and execution policies around model calls | Deep Agents; custom harnesses | The configured Agentforce workflow and its surrounding controls, conceptually |
| Configuration language | Authors state and decision controls | Code/configuration in the chosen stack | AgentScript |

The tutorial can show a generative loop nested inside a controlled graph node. A graph-based runtime does not require every step to be deterministic; a harness can use graphs to retain explicit control around flexible reasoning.

## Original teachable mechanisms

1. **One customer, two obligations.** Start with “Explain this charge, and investigate my outage.” Carry both pending tasks through every example. The classification can be mixed; the graph must retain the second task after handling the first. Completion should reflect resolved obligations, not merely an answer emitted.
2. **Classify each step before choosing its engine.** Account access is a trusted service check. Interpreting the customer's intent is a bounded semantic judgment. Explaining a disputed invoice can need generative reasoning. A service request that only needs authorized lookup may avoid a generative call entirely.
3. **Give every decision a contract.** Show a small card containing the question, state available at that time, allowed outputs, source of uncertainty, and timeout/invalid-response route. This is an application design, not a fabricated `koa-action` schema.
4. **Animate the context boundary.** The route node sees the conversation prefix and category criteria; the explanation node receives authorized invoice facts; the transaction service sees authenticated principal, account, and policy. Model interpretation never supplies authentication.
5. **Separate decision and authority.** A model may identify that a credit was requested. A deterministic step obtains eligibility and access. The backend rechecks authority at execution. If showing AgentScript, label language fragments and omitted action bindings rather than presenting them as runnable adapters.
6. **Expose the uncertainty tradeoff.** An illustrative threshold control can show automatic coverage falling as more cases are sent to clarification or review. Do not draw a monotonic empirical error curve without data; use a clearly labeled synthetic table. Include a mixed-intent route independent of numerical confidence.
7. **Include the economic failure case.** Let `D` be average specialized decision cost, `O` orchestration overhead, `L` the baseline expensive decision cost, and `f` the fraction that still incurs `L`. Under a deliberately simplified decision-stage model, candidate cost is `D + O + fL`, so savings require `D + O < (1-f)L`. This is only a mechanism illustration: whole-service costs also include tools, retries, people, integration, and unresolved work. Latency depends on the critical path and cannot be inferred by adding parallel branch times.
8. **Make the development pipeline visibly branch.** Source snapshot → groups/deduplication → train/development/locked test. Augment only after splitting and keep derivatives with their sources. Training supports permitted adaptation; development selects definitions and gates; frozen artifacts enter the locked test. Feedback goes to the next dataset, with fresh untouched evidence for a new claim.
9. **Pair evaluation with diagnosis.** Compare the same decision snapshots offline under equivalent permissions. Use a controlled service pilot for full workflow effects. If a mixed task was misclassified, inspect definitions/data; if mixed was correct but the pending task vanished, inspect state transitions. These lead to different fixes.
10. **End with a practical pilot.** Choose one frequent bounded decision that changes downstream work, declare quality limits and a minimum worthwhile cost saving, freeze the development result, and test against an appropriate baseline. Keep quality, coverage, total cost, and end-to-end latency visible together.

## Review questions for each version

- Can a learner explain the distinct responsibilities of model, graph, language, and backend after seeing the architecture?
- Are topology, relevant context, and state actually illustrated through a route, rather than only named?
- Does the learner see both a successful automatic path and an uncertainty/failure path?
- Does every displayed percentage, time, price, or curve have a source or an immediate illustrative label?
- Is the training illustration clearly a proposed task-development process, with split-before-augmentation and a locked test?
- Do visible slide text, notes, and interactive behavior all preserve the same factual boundaries?
- Are source links attached to the claims they support, with more complete evidence in notes/reference material?
