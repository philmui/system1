# Explicit live frontier lessons

Prepared lesson replay remains immutable and simulated. Opening a lesson or fetching `GET /api/lessons` does not contact a provider. Every live lesson request accepts `frontier_model`: **`gpt-4.1`**, **`gpt-5.5`**, or **`gpt-5.6-sol`**. Omitting the field preserves the GPT-5.5 default. The production Responses adapter uses the selected model even when the rest of the application runs in `test-fixture` mode. It requires the backend's `OPENAI_API_KEY`; missing credentials, unavailable models, and provider errors never fall back to fixtures or another model.

The three choices support Responses structured outputs. GPT-4.1 receives no reasoning parameter; GPT-5.5 and GPT-5.6 Sol use low reasoning effort and an 8,192-token output allowance. GPT-4.1 retains the adapter's 2,400-token allowance. These are application settings, not comparative performance claims. See the official model documentation for [GPT-4.1](https://developers.openai.com/api/docs/models/gpt-4.1), [GPT-5.5](https://developers.openai.com/api/docs/models/gpt-5.5), and [GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol).

Python LangGraph orchestrates these workflows; OpenAI calls use the Python SDK's `AsyncOpenAI.responses.parse` directly. The [LangChain JavaScript OpenAI tool guide](https://docs.langchain.com/oss/javascript/integrations/tools/openai) describes JavaScript wrappers for built-in tools, which these workflows do not invoke. `OPENAI_API_KEY` is read from the repository-root `.env` through Pydantic Settings' `python-dotenv` parser and passed explicitly to the SDK. Deployment environment variables and explicit settings can override the file; the browser never receives the key.

These lesson commands leave the operational document collection, run history, and provider configuration unchanged. Only fictional, predefined lesson sources are accepted. The API rejects unapproved browser origins and admits one live lesson command at a time across the lesson endpoints.

Each request creates and closes its own provider from copied settings. Selecting a model changes neither `.env` nor the operational workflow configuration. Unsupported identifiers are rejected before provider work. `ProviderMeta.configured_model` records the requested identifier, while `returned_model` retains the provider's actual response identifier. Discovery additionally records the model in its run configuration. A selected model is configuration; direct routes still make zero frontier calls.

## Run live classification

`POST /api/lessons/classify/live` accepts any of the five prepared classification `example_id` values, its exact `content_version`, and optional `frontier_model`. It calls **Jev** for an actual bounded judgment, executes the default taxonomy, 0.80 threshold and text guard, and calls the selected frontier model only when that actual decision requires interpretation. A direct acceptance makes no frontier request. This endpoint runs only the System 1 strategy; it does not purchase a frontier-first comparison.

Both provider credentials are checked before paid work because the live judgment can require either route. Prepared example names do not force routes. In catalogue v3 the Mixed-purpose report contains email headers and a genuine proposal to change billing and acceptance terms, so the existing text guard requires interpretation even when the live model returns report at full confidence. The previous plain progress report remains valid as a direct classification when confidently judged report; its historical prepared low-confidence recording is retained. Missing credentials and failed calls never produce a prepared fallback.

The response contains actual judgment and optional interpretation metadata, local policy timing, component and overall classification elapsed time, attempt counts, and agreement with one authored synthetic reference. A failed interpretation preserves its earlier successful judgment and policy evidence. The stopping point is category acceptance or an unapproved proposal; no human approval or publication occurs. The same evaluator powers this single strategy and the paired comparison below. Opening the page or selecting a prepared source does not call either provider.

## Interpret a prepared source

`POST /api/lessons/interpret` accepts `example_id` (`ambiguous` or `proposed`), the exact `content_version` supplied with that lesson document, and optional `frontier_model`. Extra fields, arbitrary documents, unsupported examples, and stale content versions are rejected before the provider request.

The server executes the default classification policy against the source's **prepared System 1 signal**, verifies that the route requires interpretation, and sends the retained source through `OpenAIProvider.interpret`. It does not call Jev. The response includes the executed policy receipt and actual frontier proposal, provider/configured/returned model, request ID, elapsed time, and usage when supplied. The proposal still requires review; it is not approved, indexed, or written to an operational run. One explicit action makes one request, without automatic retries.

The optional `metrics` receipt separates the entire interpretation preview from local policy evaluation and the provider round trip. It compares the returned proposal with that document's authored reference category, with one evaluated document. This is reference agreement on a synthetic example, not an accuracy estimate or completed-workflow latency. No human approval or publication is included.

## Measure two classification strategies

`POST /api/lessons/compare-classification` accepts any of the five prepared classification `example_id` values, its exact `content_version`, and optional `frontier_model`. Both live providers are checked before either strategy starts. The request runs **System 1 + exceptions** and **Frontier first** concurrently from a common start, using the same content, context, taxonomy, runtime threshold, text guard, and review obligations. The Jev strategy calls the actual bounded adapter; the frontier strategy uses a separate structured bounded-classification contract. Both strategies use the same selected frontier model. Either strategy calls interpretation when its actual judgment and the shared runtime policy require it. The frontier baseline therefore can consume more than one call.

The response records component elapsed time, provider metadata, policy time, queue time, actual request attempts, observed provider work, and each strategy's elapsed interval. Its stopping point is an accepted category or an unapproved proposal. An endpoint's total time is neither the sum of concurrent strategies nor time through human approval and publication. At most two provider requests run concurrently; the configured capacity can reduce this to one. The resulting differences belong to this concurrent trial and can reflect shared queueing or provider contention.

Each judgment and final preview is separately compared with one authored source reference as `matching / evaluated`. They concern the same document and must not be aggregated as independent samples. A failed stage has no output reference denominator; an earlier valid judgment and measured failed work remain visible. The equal numeric acceptance threshold is a policy assumption, not evidence that the models' confidence signals are calibrated or comparable probabilities. No estimated cost or benchmark accuracy is inferred from these observations. There are no automatic retries in this paired preview.

## Find or compare policy sources

`POST /api/lessons/discover` accepts `example_id` (`find` or `compare`), optional `frontier_model`, and `bounded_mode` (`prepared` or `live`, default `prepared` for compatibility). It prepares and indexes the two fictional policy versions using fixtures in a temporary store, then executes the existing Discovery graph with a fresh engine. That source preparation is explicitly outside the returned discovery run's timing and call counts. The returned snapshot and document records are self-contained and disappear from server storage when the command ends; their IDs are not operational API resource IDs.

- In **prepared** mode, Find uses a prepared intent signal, deterministic lexical retrieval, and prepared relevance screening. Its clear route requires zero frontier calls and can run without an OpenAI key. Compare calls the selected frontier model for planning and, when retrieved evidence permits, answer composition; relevance and semantic support stay prepared.
- In **live** mode, both keys are required before execution, including Find because its actual intent can require planning. Jev supplies real intent, relevance, and support signals; the selected frontier model performs whichever planning or generation the actual route selects. The lesson title never forces its expected route. This mode records live provider metadata and actual component elapsed time.

Both modes execute exact citation checks against retained passages. Optional metrics derive overall elapsed time from this run's start and terminal events, excluding source preparation. Intent reference agreement uses one authored task label. Citation metrics count **claims** entering, passing, and failing the citation check; support metrics count claims entering and retained by the fallible semantic check. Missing checks remain unavailable, and these counts do not establish overall answer accuracy.

Actual provider errors remain visible in the returned execution record. The ordinary runtime's single bounded retry for retryable failures remains active for this workflow, and its attempt count includes those retries. There is no fixture replacement for a failed frontier call.

## Timing and configuration

`POST /api/lessons/review/live` accepts a fixed fictional `page_id`, its exact `content_version`, `action` (`classify` or `redact`), and optional `frontier_model`. It returns actual structured judgment or a redaction draft plus measured provider metadata. Source replacements are validated exactly; that check does not certify that all personal information was removed. Both responses require review and create no operational publication. The live pane and the prepared strategy comparison remain separate.

Provider `elapsed_ms` measures client-observed request work, including network delay and response processing. It is not a measurement of pure model inference. Discovery's full elapsed time includes local runtime work; prepared bounded mode also includes simulated bounded-provider delays. Its provenance explicitly distinguishes those sources; simulated System 1 durations must not be compared as measured model performance.

The standard `OPENAI_MODEL` default is `gpt-5.5`. An explicitly configured different model remains respected by ordinary operational workflows. Dedicated lesson actions use their request's allowlisted selection, defaulting to GPT-5.5. GPT-5.5 and its dated snapshots and GPT-5.6 Sol use low reasoning effort with an 8,192-token output allowance; other configured models keep their existing options. SDK retries remain disabled, and all requests use structured outputs with storage disabled and no tools.

`tests/test_live_lessons.py`, `tests/test_classification_measurements.py`, and `tests/test_frontier_selection.py` mock the Responses and TypeSafe SDKs to verify model selection across each endpoint, strict source binding, safe errors, attempt counts, origin/admission rules, cancellation, operational isolation, equal classification contracts, partial outcomes, actual discovery route changes, and citation/support checks. Mocked durations are test observations, not published model measurements. Real service measurements require an explicitly executed live request.

The integration attempt in this environment on September 29, 2026 failed with a provider connection error. No GPT-5.5 response or inference-performance measurement was obtained. The production path is implemented and tested with SDK mocks; successful service access remains unverified here.
